# 加密本機身分歷史

`IdentityHistory` 管理一個裸 libgit2 儲存庫，固定放喺應用程式資料目錄內嘅 `identity-history-v1.git`。主程式必須提供私人應用程式資料目錄，唔可以用目前項目、工作目錄、便攜匯出位置或者原始碼工作目錄。目錄必須已存在，上層路徑唔可以包含符號連結或者 Windows 重新分析點。儲存庫必須係裸儲存庫，而且冇遠端。

## API 同儲存

明確呼叫 `initialize` 會登記獨立歷史憑據、喺作業系統憑據庫建立隨機 256 位元加密密鑰，再初始化裸儲存庫。唔會覆寫已存在或者初始化到一半嘅狀態。原生憑據庫用唔到時冇明文後備途徑。

`append` 係受信任內部變更接收端，只接受產生嘅 32 位十六進制身分 ID、白名單動作同只可移動嘅快照。改名後沿用同一身分 ID，標籤唔可以作識別碼。呼叫端將還原所需嘅身分中繼資料同可選驗證器種子序列化到只可移動嘅 `Secret`。包含種子嘅明文留喺記憶體，任何物件寫入之前要先加密。PIN、密碼、當前／下一個驗證碼同復原答案全部唔可以入快照。現用憑據留喺專屬原生憑據庫記錄。服務本身唔會管理現用身分或者負責序列化。

每個新第 2 版事件使用隨機 256 位元事件密鑰，寫入一個用 AES-256-GCM 加密嘅 blob，再新增只可附加嘅提交，上層係上一個事件。認證會將密文綁定版本、動作、身分 ID 同隨機事件 ID。提交中繼資料只包括呢啲已遮蔽欄位同固定本機作者。刪除身分仍然保留歷史事件。冇歷史改寫、網絡同步或者還原 API。經授權嘅保留操作會移除所選現用事件密鑰，但唔刪歷史提交。只可以匯出下面列明嘅中繼資料，快照同標籤明文絕不匯出。

每次 `read` 都獨立核實歷史憑據。每次最多 16 個快照，每個最多 1 MiB，偏移量唔可以超過 10,000。只會沿已錨定嘅歷史鏈行，呼叫端唔可以任揀物件 ID 或檔案路徑。載入提交、樹同 blob 前會先驗證標頭大小。不明動作、格式錯誤 ID、預期以外嘅樹條目、非 blob 項目、合併提交同認證失敗都會拒絕。喺服務實例生命週期內，憑據嘗試失敗會使用共用逐級限制。每次應用程式執行應保留一個服務實例；重建會重設記憶體內節流，唔可以當成跨程序防護。

`replace_credential` 先核實舊獨立歷史憑據先更換，保留快照密鑰，所以歷史密文仍可讀。憑據更換嘅審計事件要由協調元件附加，更換同附加唔係同一個原子操作。

## 失敗同威脅界限

憑據庫另外保存預期最新提交 ID。缺少密鑰、憑據、錨點或者儲存庫，或者實際最新提交同憑據庫錨點唔一致，都會停止讀寫。第 2 版加密密鑰儲存區另有原生憑據庫 HMAC 錨點同內嵌預期歷史頂端，兩者都要吻合。程序內互斥鎖加應用程式資料目錄嘅獨佔鎖檔會將合作存取順序化。更新參照時亦會比對預期上層。

原生憑據庫、密鑰儲存檔同 libgit2 唔共用原子交易。先原子取代密鑰儲存檔並設好錨點，先發佈預期新歷史頂端。後續任何一步失敗，之後操作就會停止。未完成嘅 `.pending` 檔亦會阻止存取。需要先獨立驗證保留嘅物件同憑據庫記錄，再明確經支援途徑復原。唔可以自動接受新頂端、重新配匙或者刪除儲存庫，因為會抹走證據。初始化失敗亦要保留並標示為部分完成。

呢個設計保護已儲存快照，減低一般檔案系統暴露風險，亦會根據完好嘅原生錨點偵測儲存庫回滾。無法防範控制同一個已登入作業系統帳戶、可以讀原生憑據、修改執行中程序，或者同時還原兩套儲存嘅人。主程式必須將應用程式資料目錄限制為只限擁有者存取。呢個模組未有證明介面整合、還原流程、實際身分協調或者封裝後執行成功。

## 建置同驗證

已有 `libgit2::libgit2package` 目標時，本機安全 CMake 子目錄會定義 `libslic3r_identity_history`，連結核心加密服務同 libgit2。測試子目錄將 `identity_history_tests` 登記為獨立執行檔同 CTest 測試，所以 `main` 唔會同核心測試衝突。冇 libgit2 嘅獨立設定會清楚提示未能使用，唔會聲稱已驗證歷史。

行為測試包括加密來回讀寫、附加保留、穩定 ID、原始物件中繼資料遮蔽、快照機密性、獨立憑據、更換憑據、讀取界限、無效輸入、缺少／錯誤密鑰、憑據庫不可用、頂端同錨點不符、錨點寫入中斷，以及嘗試節流。只用純記憶體測試憑據庫同隔離臨時裸儲存庫。已用 MSVC 19.51 配合指定配方建置嘅 libgit2 1.9.3 編譯執行，輸出 `PASS 57 identity history checks`。呢個結果只涵蓋服務，未驗證原生歷史面板或者完整封裝流程。

## 中繼資料、標籤同已遮蔽匯出

`read_metadata(answer, offset, count)` 同 `read` 用同一獨立憑據同分頁限制，但回傳 `IdentityHistoryMetadata`，唔會解密快照。`read_revision(answer, revision)` 先驗證身分，最多沿 10,000 個可達事件搜尋，只解密指定嘅現用快照，已修剪目標會被拒絕。其他列經修剪唔影響一般分頁讀取，已留墓碑嘅列內容為空。每列包括修訂、穩定身分、白名單動作、以 UTC 秒記錄嘅提交時間、以分鐘計嘅時區偏移、格式版本同修剪狀態。提交時間唔係截圖來源證據，亦唔係可信外部時鐘。`read` 會提供同一組欄位，並保留只可移動嘅快照。

`append_label(answer, identity, label)` 為穩定身分新增加密 `Labelled` 事件。標籤必須係有效 UTF-8，長度 1 至 256 個位元組，唔可以包含 ASCII 或 C1 控制字元。`read_label(answer, revision)` 最多行 10,000 個已錨定事件，只有所選事件確實係標籤先會以只可移動嘅 `Secret` 傳回解密文字。呢個 API 唔可以取回一般身分快照。標籤按時間順序新增，唔會覆寫提交訊息或者自動取代早期標籤。

`export_redacted(answer, offset, count)` 回傳有上限嘅 JSON，只包含該頁中繼資料。特登排除標籤、快照、密文、密鑰、憑據記錄、內容長度同按內容產生嘅雜湊。函式唔會揀目的地或者寫檔。`redacted_diff(before, after)` 只會比較兩列係咪同一身分、白名單動作有冇轉變，唔會做內容語義比較。

### 第 2 版保留機制同容量限制

新事件使用第 2 版格式同獨立隨機事件密鑰。有大小上限嘅 `identity-history-keys-v2.enc` 位於裸儲存庫旁邊，唔會放喺佢入面。現有原生憑據庫主密鑰以 AES-256-GCM 加密檔案；另一筆固定原生憑據庫記錄用 HMAC-SHA-256 認證密文。唔會為每個事件建立一份憑據。已初始化而且有事件嘅一般歷史佔用四筆固定原生憑據庫記錄：獨立憑據、主密鑰、歷史頂端錨點同密鑰儲存錨點。

密鑰儲存區最多 512 把現用密鑰同 4096 個明確墓碑，密文上限 196608 個位元組。使用前會驗證數量、正文確實長度、事件 ID、重複項目、現用集合與修剪集合互不重疊，以及預期歷史頂端。密鑰直接序列化入單一個會抹除內容嘅 `Secret` 記憶體區。資料先寫入獨佔建立嘅待處理檔，完成寫入同步後原子改名。待處理檔中斷、記錄缺失、密文變更、檔案回滾或者頂端不匹配，都會阻止存取。即使連舊密鑰儲存檔同舊錨點一齊還原，內嵌頂端同現有歷史唔同仍會失敗。同時回滾全部憑據庫同歷史狀態就超出保護範圍。

`capacity(answer)` 回報確實現用密鑰數、墓碑數同各自上限。儲存區滿就拒絕新事件。每次修剪都要留一把新審計事件密鑰，所以修剪一項只會用審計密鑰取代一把現用密鑰；修剪兩項或以上先可能釋出現用容量。審計事件本身唔可以修剪。墓碑同審計事件會喺明確限制內累積。容量耗盡需要另外設計遷移，唔會靜靜淘汰資料、無限增加憑據或者跳過限制。

`preview_prune(answer, revisions)` 接受 1 至 16 個不重複而且可達嘅事件修訂，最多行 10,000 個提交。不明、已修剪、第 1 版同修剪審計事件一律拒絕。不透明 `HistoryPrunePreview` 綁定確實選取列、目前歷史頂端同所屬服務實例。`rows()` 只向原生確認面板提供中繼資料。

`prune(answer, preview, confirmation)` 重新驗證身分，再核實上述綁定，之後先消耗唔依賴 UI 工具包嘅 `GUI::SuperConfirm::State`。`may_fire()` 要求兩個獨立確認都開啟、滑桿到 100%、已授權，而且未取消。唔接受單一布林值作授權參數。驗證失敗唔會消耗狀態；真正執行時會重設並取消狀態，避免原封再用。呼叫端必須提供原生確認互動產生嘅狀態。呢個係程序內介面約定，唔防範同程序入面運行嘅惡意程式碼。

修剪會由現用加密儲存區移除所選密鑰，並將對應事件 ID 記為墓碑；新 `Pruned` 事件嘅加密審計內容會記錄所選修訂。原有提交同密文保持原樣。`read` 同 `read_metadata` 保留相關列並標示 `pruned=true`，`read` 對已修剪內容回傳空 `Secret`，已修剪標籤無法讀取。缺少密鑰但冇墓碑就屬損毀，唔可以推定為修剪。審計提交、更新後嘅儲存區同兩個錨點以附加事件相同嘅失敗停止次序更新。操作失敗可能要明確復原已經移除嘅應用層密鑰或者保留嘅加密物件，唔可以聲稱已原子回滾或者成功修剪。

第 1 版快照仍然用原有主密鑰讀取，包括第一次新增第 2 版事件後嘅混合歷史。唔容許選擇性修剪第 1 版，因為移除共用密鑰會破壞其他舊記錄同第 2 版密鑰儲存區。唔會改寫或者暗中重新加密第 1 版歷史。

**移除現用密鑰唔等於法證級清除。** 之前讀取過嘅明文、較舊憑據庫狀態、備份、檔案系統日誌同外部副本都可能保留可復原資料。操作只會經已驗證儲存途徑移除目前應用程式嘅現用解密密鑰。原生介面必須保留呢項說明，唔可以聲稱永久銷毀全部副本。

### 保留機制驗證

合成測試亦涵蓋原生確認狀態、單次使用、過期或屬於其他實例嘅預覽、無法到達或重複選取、讀取第 1 版同拒絕修剪、混合版本、只可附加審計、持久保留已修剪列、拒絕解密修剪後標籤、密鑰儲存回滾、舊錨點重播、儲存檔缺少或損毀、錨點寫入中斷、待處理檔、固定憑據庫記錄數，以及確實 512 把密鑰界限同容量重用。只用臨時合成歷史同記憶體憑據庫測試資料。要記錄實際執行指令同結果，唔可以將來源存在當成已驗證。

### 已執行嘅保留操作驗證

用支援嘅 MSVC、OpenSSL C ABI 同本機建置嘅 libgit2 1.9.3 編譯並執行最終合成測試，結果如下。

```text
PASS 118 identity history checks
```

使用現有測試程式嘅 `--msvc --compiler cl --history-only`、相符 OpenSSL 標頭同 DLL 參數，以及指向支援依賴安裝嘅 `--libgit2-prefix`。冇用真正原生憑據庫記錄或者使用者歷史。

三個獨立編譯嘅臨時原始碼副本，分別移除原生 `may_fire()` 檢查、預覽擁有者／頂端綁定，以及第 1 版拒絕修剪。三者都成功編譯，行為測試都如預期失敗。喺隔離副本還原原始碼後，118 項檢查再次通過。使用相同依賴參數，以 `--history-negative` 取代 `--history-only` 就可以重做。
