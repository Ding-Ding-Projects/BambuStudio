# Required-feature coverage

This reviewed inventory records 117 stable public feature identities across nine surface classes. It does not claim that every feature is implemented or verified. The matrix is `design/required-feature-coverage.json`; the existing native delivery and gap records remain historical evidence and are not overwritten.

## Find the relevant workflow

Start with the surface you use: native workspace, owned embedded views, third-party embedded pages, LAN sender, LAN setup companion, build companion, documentation companion or public documentation. Repository delivery is a separate evidence owner for builds, releases and project records. Each feature has an explicit record for every surface, including conditional, externally owned, suspended and nonapplicable cases with reasons.

Missing inventory identity is not evidence that implementation is absent. Historical family presence stays in `historicalReferences` and never assigns `partial` implementation status to native or embedded surfaces. `source-verified` is used only for specifically linked source units. All per-class runtime states remain `unverified` in this candidate.

The separate `nativeIndividualSurfaces` inventory preserves all 28 exact IDs, source anchors and required states from the pinned native delivery record. These include native and embedded surfaces, not 28 native-only windows. Class links organize review; embedded ownership remains unresolved. Individual feature applicability, nested dialogs and per-state acceptance remain pending. The 1,053 class records are not a complete individual-surface matrix.

The LAN setup, build and documentation companions have explicit single-portable-executable format obligations instead of Squirrel installer obligations. The native application retains its installer requirement. The window-wide vocabulary-drop requirement explicitly excludes the public documentation website; separate upload and privacy obligations remain. Third-party embedded content requires feature-specific ownership review, with owned-container duties retained, rather than a blanket impossibility exemption.

## Preserve existing findings

Fifteen legacy families have explicit crosswalks. Some map to several public identities, such as documentation delivery or bundled fonts. These are reviewed semantic links, not automatic equivalence or resolved findings. Independent review confirmed identity preservation, the 28 historical surface references, format exceptions and truthful pending states. It did not establish complete individual applicability or runtime acceptance. Do not delete old findings or promote their statuses when extending this inventory.

Known source units link the Preferences geometry documentation, Base64 conversion and direct LAN sending milestones. Their bounded evidence must be reviewed separately before assigning runtime acceptance to any tuple. A complete matrix requires real behavior, localization, persistence where applicable, negative checks and genuine built-surface evidence.

## Check consistency

Run `node scripts/ci/check-required-feature-coverage.mjs --self-test`. The checker contains handwritten expected lists independent of generated rows: 117 identities, nine classes, 28 individual IDs and 15 legacy families. Nine negative mutations cover omissions, missing format exceptions, an incorrect website-drop claim, inherited historical status and an unproven third-party exemption. These checks do not verify the remaining applicability reasoning, implementation, visual quality or runtime claims.
