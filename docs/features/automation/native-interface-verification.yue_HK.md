# 託管原生介面驗證

執行 `37139071425` 傳回空的目標桌面控制代碼，原生代碼係零；未到桌面名稱查詢。下一個有界觀察會用 `THREAD_QUERY_LIMITED_INFORMATION` 開啟已確認的確切執行緒，將所屬程序同已接受的目標 PID 比對，並要求 `GetExitCodeThread` 成功傳回 `STILL_ACTIVE`。所擁有的執行緒控制代碼會一直保持開啟，直至現有桌面查詢完成，再喺 `finally` 關閉。開啟、程序查詢、退出查詢或關閉失敗時，只記錄即時數值原生代碼同固定階段。成功、身分、存活及關閉欄位都係布林值；呢啲觀察唔會新增執行緒 ID、程序 ID 或控制代碼值。桌面必須完全相同，查詢不可用仍然會阻止 `g`。冇重試、目標函式呼叫，亦唔會用父桌面證明代替。現有九項託管案例涵蓋真正輔助程式路徑：控制代碼不可用、擁有者不可用或不符、退出查詢失敗、執行緒已退出、桌面例外、關閉失敗及成功，包括呼叫同清理次序。新增部分已喺驗證器 `75770f71f59358514df9d5af42b38402e538116c` 的託管契約執行 `37139896660` 通過。修改後的診斷 `37139898854` 確認咗確切執行緒擁有權、指定情境下的退出狀態證據及關閉，但仍取得空桌面控制代碼，原生代碼係 0。名稱查詢同繼續執行都未到達。拆除已驗證。冇喺本機執行。進一步歷史套件診斷暫停，等候目前套件的執行證據。

`STILL_ACTIVE`（259）只係指定情境下的退出碼證據：目標仍停喺已確認的偵錯器初始中斷，亦未寫入繼續執行命令。佢唔係一般執行緒存活證明，因為已終止的執行緒亦可以用 259 作為退出碼。`thread_alive` 欄位只記錄呢個情境比較，唔可以取代偵錯器狀態、桌面、擁有權或拆除證明。

執行 `37103711674` 的啟動診斷，喺確認訊號、唯一目標身分同兩項 Job 成員檢查之後，到達目標桌面查詢。桌面比較係空值，代表查詢喺比較之前拋出例外，唔係觀察到另一個桌面。查詢而家分別記錄 `GetThreadDesktop` 同 `GetUserObjectInformationW` 的固定階段、控制代碼是否存在、查詢是否成功，並只喺傳回失敗時即時擷取數值原生錯誤。所需位元組上限係 65,536，另有明確上限旗標。呢啲觀察唔會新增名稱、控制代碼、執行緒識別碼或例外文字。繼續執行之前仍然要求桌面完全相同、初始確認、擁有權檢查同 90/120 秒期限。現有九項託管契約案例而家包含實際觀察函式對空控制代碼、資訊查詢失敗、成功、長度超限，以及兩個原生邊界例外的結果。新增部分未喺本機執行，需要託管驗證。尚未識別到失敗的 DLL 初始化函式。

`scripts/ci/Verify-HostedNativeInterface.ps1` 會喺即棄 GitHub 託管 Windows 執行器安裝已發佈的 Squirrel 套件，將佢綁定到指定來源提交，再執行一個原生介面範圍。實作仍等候第一次託管執行。新增期間冇產生本機執行或擷取證據。

## 呼叫方法

每個全新託管工作只執行一個範圍。將示例標籤同提交換成確切候選版本；工作目錄必須位於該來源提交。

```powershell
./scripts/ci/Verify-HostedNativeInterface.ps1 `
  -Tag md3-v123 -ExpectedSourceCommit <40-character-candidate-sha> `
  -Repository Ding-Ding-Projects/BambuStudio `
  -OutputDirectory "$env:RUNNER_TEMP/native-interface-evidence" `
  -Scope menus -Language en -Theme light -Scale 1 -Viewport 1200x800
```

## 矩陣及證據

參數接受 `en`、`yue_HK`、`bilingual_en_yue_HK`；`light` 同 `dark`；比例 `1`、`1.25`、`1.5`、`2`；客戶區 `1200x800` 同 `1000x600`。呼叫者要提供指定比例的真實顯示器。呢個指令碼唔會改變系統 DPI 或合成縮放。即時版面標頭同每個擷取的原生視窗都必須報告指定 DPI。客戶區大小透過原生視窗尺寸操作量度及調整，最多四次。不支援的最小大小或比例係失敗，絕唔係通過式略過。

驅動程式用固定版本的 `lowlevel-computer-use-cheap` 路徑，喺所擁有的隱藏桌面執行點擊、文字、鍵盤輸入同 PrintWindow 擷取。一個短暫輔助程式喺該桌面觀察原生 UI Automation，並將鍵盤輸入送到實際有焦點、屬於本次工作的控制項。UI Automation 模式只作唯讀用途。冇 InvokePattern、ValuePattern setter、WM_SETTEXT、`invoke`、`menu-popup` 或其他應用測試命令變更。現有 `app.probe()` 路徑會啟動 `send-layout-probe.py` 作唯讀觀察，唔係輸入機制。唔使用修飾鍵捷徑，因為固定版本的背景按鍵實作已記錄：檢查實體修飾鍵狀態的控制項有相關限制。

每個成功輸入步驟都會擷取結果中有焦點的介面。原始記錄包括原生名稱、焦點、啟用狀態、矩形、觀察耗時、版面探測溢出量度、圖片尺寸同 SHA-256。外層收據綁定發行版本、來源提交、可執行檔雜湊、發行資產雜湊、驅動程式雜湊、託管執行及指定／觀察組合。觀察耗時包括自動化開銷，唔係介面延遲基準測試。

每個範圍最多保留 30 張圖片，另加 `install.json` 同 `runtime.json`，符合現有 32 檔案、64 MiB 自動化證據邊界。包裝程式保留 `bambu-automation-v2` 封套同專用 `hosted-automation-public-v1.pem` 收件者。使用 `scripts/md3/Open-HostedAutomationEvidence.ps1`，提供預期執行、提交、標籤及可執行檔雜湊，進行解密同驗證。

託管產物上傳只應包含 `receipt.json`、`envelope.json` 同 `evidence.aesgcm`。原生觀察、檔案選擇器圖片、暫存設定檔路徑同未審閱像素留喺加密套件入面。可公開收據只包含數量同固定範圍／組合值，唔包含原生標籤或路徑。解密驗證完整性，唔代表批准私隱或發佈。公開之前要審閱每張圖片。本文冇用偽造截圖代替仍待完成的審閱。

用詞同持久化範圍分別保留 28 同 25 張圖片。第一個有效映射之後，`neutral-malformed.json` 包含不完整 JSON 物件，介面必須明確拒絕，同時保留該映射的標題像素。提交現有不支援結構版本 2 測試檔之前，第二個有效替換必須恢復啟用狀態。呢次獨立拒絕必須保留第二個映射。兩個檔案都係喺隔離暫存目錄產生的中性測試資料，唔會上傳私人用詞檔。每個顯示檢查點會等候兩個相同標題裁切，最多六次觀察，並保留產生穩定裁切的完整原始圖片。暫態穩定性樣本仍屬受限暫存資料；所有逐次輸入擷取同已接受穩定圖片都會留喺加密套件。全程要求原有原生無障礙文字不變。像素差異及相等證明顯示變更同還原，唔證明確切文字內容；保留圖片仍須人手審閱。

### 真正標題 getter 觀察

現有 Preferences 標題 `Label` 有穩定名稱 `personal-vocabulary-title`。當 `BAMBU_AUTOMATION=1` 而現有版面探測已啟用，該具體控制項另外報告 `native_getters` 版本 1。原生程式碼直接喺同一個 `Label` 實例呼叫 `GetLabel()`、`GetLabelText()` 同 `GetUnwrappedLabel()`。只輸出兩個布林值 `getLabelTextEqualsGetLabel` 同 `getUnwrappedLabelEqualsGetLabel`；現有 `label` 欄位本身已經係真正 `GetLabel()` 值。冇用顯示轉接器、UI Automation 名稱或快取 Python 文字代替 getter 呼叫。

用詞範圍要求恰好一列指定名稱的探測記錄，佢必須同可見無障礙標題有相同正值 HWND 及頂層控制代碼、相符螢幕幾何、原有原生標籤文字，以及兩個精確布林結果。每次接受穩定標題擷取之前同之後，都記錄相符 getter 觀察：基準、第一映射、語法錯誤拒絕、替換、不支援版本拒絕及清除。呢個唔會喺 28 張圖片流程以外加圖。已換行或帶快捷字母標記而唔符合完全相等的標題會令觀察失敗；唔會用空白正規化製造相等。目前短而未換行的英文標題係第一個預定託管組合。其他語言、主題及大小組合仍各自未驗證。

呢份證據只適用於被拍攝的標題控制項，唔證明所有 getter 使用者、操作比較、日誌、匯出或其他自訂介面。持久化範圍保留現有無障礙／像素契約，唔會悄悄升級成三 getter 證據。繪製、日誌、匯出及持久化實作不變。

`scripts/md3/test_native_vocabulary_observation.py` 有九項來源隔離案例，使用正式 getter 判斷式同用詞序列，拒絕缺少／含糊控制項、錯誤 HWND／幾何／原文、非布林 getter 結果同不相容結構。刻意移除真正未換行比較，會暴露同一個錯誤觀察。指令化觀察亦檢查兩個保留分支、兩者之間成功重設狀態，以及 28 張圖片數量。呢啲係協調契約，唔係模擬原生證據。現有託管執行工作流程會喺安裝之前，只用 Python 標準函式庫執行佢哋。只喺託管執行器執行：

```powershell
python scripts/md3/test_native_vocabulary_observation.py -v
```

同一工作流程接受 `vocabulary_contract_only=true`，啟動一個五分鐘 Windows 工作，取出所派發工作流程提交，只執行該九項來源隔離案例。唔需要發行版本、安裝程式、原生編譯或產品程序。收據將確切工作目錄綁定到 `GITHUB_SHA`、執行同嘗試次數、驅動程式及契約 SHA-256，以及實際退出碼。只保留 `receipt.json` 同 `output.txt`。候選版本整合同推送之後先派發：

```powershell
gh workflow run native-interface-runtime.yml --repo Ding-Ding-Projects/BambuStudio --ref feature/ui-integration -f vocabulary_contract_only=true
```

呢個自選路徑忽略發行同互動參數，永遠檢查所派發來源，唔會用 `expected_source_commit` 選另一份工作目錄。同時設定 `provision_resolution=true`，會喺任何顯示或產品工作之前，由獨立驗證工作判定失敗。新開關省略或為 false 時，安裝路徑仍要求有效發行標籤、確切來源 SHA 同受支援互動範圍，先可以取出來源或安裝。來源限定工作通過，唔代表原生 getter、繪製字句、已安裝應用或啟動已驗證。

呢個擴充冇喺本機執行測試、原生編譯或產品。原生編譯、九項託管契約同真正已安裝互動仍待完成。

持久化範圍會停止所擁有程序、驗證拆除，再用同一隔離設定檔啟動另一個程序，要求映射標題像素保持相等。可見清除操作之後，第二個全新程序必須恢復基準像素同 Load JSON 控制項。驅動程式唔會喺兩次啟動之間複製或重建顯示快取。呢個測試程序終止之後的持久化，唔聲稱應用正常關閉。

## 失敗及復原

### 隔離啟動診斷

獨立 `hosted-startup-diagnostic.yml` 工作流程，使用另外識別的目前驗證器，診斷固定 `md3-v190` 套件（產品提交 `35d1074faea221fa4f289f1db1e0ee428a90d701`）的啟動。只喺即棄託管 Windows 執行器運作，工作上限 20 分鐘。固定 `startup-diagnostic` 範圍只啟動及停止所擁有應用，冇功能輸入、截圖、顯示配置或最小大小互動。正常驗證仍要求驗證器工作目錄同產品來源完全相符。

診斷分開驗證產品發行、安裝程式、可執行檔身分，同驗證器提交。加密 `runtime.json` 亦綁定 `startup_diagnostics.VERIFIER_FILES` 列出的全部 11 個固定驗證器檔案，使用 CRLF 轉 LF 正規化後的 `sha256-lf-v1` 雜湊。開啟證據時，管理閱讀工具另外要求 `-ExpectedVerifierCommit` 同 `-ExpectedVerifierManifestPath`。清單要由確切驗證器提交獨立建立，絕唔可以由下載證據取得。欄位係 `source_commit`、純量 `hash_format` 同 `files`，每個固定路徑都映射到其 SHA-256。閱讀工具喺建立私人輸出之前逐項比較。

有界啟動收據同 stdout/stderr 資料留喺加密證據內，而且只喺拆除已驗證、記錄操作數為零之後收集。只上傳固定收據、封套及密文。完成診斷仍保留公開產品狀態 `failed` 同 `diagnostic_only=true`，唔可以滿足已安裝功能、取消、用詞或視覺檢查。本文記錄時，[37095786787](https://github.com/Ding-Ding-Projects/BambuStudio/actions/runs/37095786787) 仍喺排隊。呢度冇聲稱啟動結果或原因；較早的零操作失敗仍未解決。

同樣完成持有者身分同拆除檢查之後，啟動診斷亦只檢查隔離啟動設定檔的直接 `log` 目錄。收集會拒絕有重新解析點祖先的路徑，枚舉上限 64 項，最多接受三個原生日誌檔名：所啟動 PID 的 `studio_<timestamp>_<pid>[_enc[_cn|_dc]].log.<counter>` 或 `crash_<timestamp>_<counter>.log`。每檔上限 512 KiB，總共 1.5 MiB。超限或不安全收集會報告不可用，唔保留部分日誌內容。唔會收集設定檔或其他設定目錄。日誌位元組同檔名留喺加密 `runtime.json`；現有 11 檔驗證器清單已綁定改動後的收集器。呢個係新增診斷覆蓋，唔係啟動原因或成功啟動證據。

啟動限定範圍另外要求每次呼叫隔離的啟動器追蹤。持有者由其收據檔名衍生新目錄，傳入一份複製的 Unicode 子程序環境，只替換 `TEMP` 同 `TMP`。控制器同持有者的程序環境都不變。正常啟動路徑保留環境繼承行為。目錄必須位於託管暫存根目錄之下，祖先冇重新解析點，而且少於 220 字元，符合現有原生啟動器追蹤路徑限制。拆除驗證之後，收集器核對私人持有者收據的確切衍生目錄，只讀取 `bbs-launcher-trace.log`，上限 64 KiB。內容保持加密；追蹤缺少或無效都唔可以確立原因。觀察現有啟動器診斷唔需要重新編譯產品。

### 從建立程序開始的載入器儀器化診斷

獨立啟動追蹤工作流程有明確 `from_creation` 模式，固定使用同一個 v190 產品及來源。保留已簽署 Microsoft CDB 探索、五分鐘偵錯器啟動期限，並獨立驗證目前驗證器。呢個模式只作診斷，絕唔提供功能或已繪製介面證據。

現有暫停啟動 Job 輔助程式有一個嚴格驗證、識別桌面的進入點。固定工作程序只喺分配 Job 之後，先喺所擁有隱藏桌面開始；CDB 建立已安裝產品並保留初始中斷點。繼續之前，工作程序要求已輸出的初始標記、確切目標 PID／執行緒、載入器旗標讀回、即時可執行檔／設定檔／啟動身分、目標桌面，以及偵錯器同產品都屬於確切具名 Job。命令檔使用 `!gflag +sls` 同固定例外／退出觀察，唔用軟件中斷點、可執行檔修補、登錄旗標或任意命令。普通附加路徑保持分開。

建立路徑使用全新私人符號快取，同固定 Microsoft 符號伺服器 `https://msdl.microsoft.com/download/symbols`。CDB 接收 `-sins` 忽略繼承的符號／映像搜尋路徑，同 `-ses` 要求確切符號配對。固定命令檔停用 `SYMOPT_LOAD_ANYTHING`、強制載入 `ntdll.dll` 符號、私人保留 `lmv m ntdll`，再執行現有載入器旗標寫入／讀回。呢個係偵錯器強制模組同 PDB 身分配對，唔係獨立 PDB 雜湊驗證。快取參數唔可以提供第二個伺服器、UNC 共用或符號路徑運算式。唔上傳快取或原始模組路徑。

符號下載同載入共用現有 90 秒觀察期限及 120 秒隔離期限。缺少或不符符號唔會放寬確認：冇輸出載入器旗標讀回，工作程序就絕唔發送 `g`。執行 `37101357236` 確立咗缺少符號的邊界，唔係失敗的 DLL 初始化函式：初始標記存在，但 `!gflag` 無法解析 `nt!_PEB` 的 `NtGlobalFlag`，所以目標從未繼續執行。新路徑同擴充後九項託管命令契約仍未執行。

受支援搜尋路徑同配對選項見 Microsoft 的[符號路徑](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symbol-path)及[符號選項](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/symbol-options)參考。冇硬編碼 PEB 位移，亦冇忽略符號不符。

由 `e50f5dac1074055e02be230bfdc5dd98d829e5e6` 驗證的執行 `37102257995`，載入相符 `ntdll` 符號並輸出載入器旗標讀回，但冇記錄成功擁有權確認或繼續執行。最終保留日誌唔可以證明呢啲位元組喺期限內幾時可用，彙總收據亦無法指出邊個擁有權條件不可用。佢冇識別失敗的 DLL 初始化函式。

因此診斷喺確認、清單、目標身分、偵錯器及目標 Job 成員資格、目標桌面、繼續命令寫入／flush 及輸出排清周圍記錄固定階段。可空布林值區分未嘗試檢查同負面觀察；數量只包含已觀察緩衝位元組及配對清單大小。冇新增 PID、桌面名稱、設定檔、命令列或例外文字。`continuation_written` 只喺現有寫入同 flush 傳回之後先變 true，唔係目標已執行初始化函式的證據。原有短路判斷、嚴格符號命令及 90/120 秒期限保持不變。

現有確認契約案例另外呼叫正式擁有權鏈，涵蓋空／含糊清單、錯誤目標、每一項 Job 成員資格失敗、錯誤桌面及完整成功。佢驗證短路呼叫同清單例外的固定階段。新增斷言仍待託管執行；原有九案例清單不變。

偵錯器輸出排清時，保留位元組上限 1 MiB，超限就停止診斷。觀察最多 90 秒，外層 Job 監督器上限 120 秒。只有整個程序樹終止同桌面關閉已證明，包裝程式先可以讀取及加密有界報告同日誌。拆除未知就唔提供證據。產品、驗證器、偵錯器同修改後輔助程式身分留喺已驗證診斷傳輸內，絕唔上傳原始日誌。冇相符符號的模組相對位移唔會識別來源常式，而載入器錯誤 1114 本身亦唔識別失敗模組。聚焦託管命令契約檢查初始確認拒絕，以及冇附加／略過初始中斷旗標。依賴新模式之前，仍需來源審閱同託管執行。

Microsoft 記錄咗[初始中斷點](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/initial-breakpoint)同[程序偵錯器旗標擴充](https://learn.microsoft.com/en-us/windows-hardware/drivers/debuggercmds/-gflag)。

目標不存在、含糊或已停用，都令相關範圍失敗。提供者逾時、觀察截斷、錯誤程序擁有權、缺少原有標籤、意外確認狀態及版面溢出都仍然係失敗。原生輔助程式有 22 秒看門狗；控制器每次最多等 25 秒取得結果。現有託管程序持有者負責應用同桌面拆除。範圍要通過，必須先驗證拆除。

先執行基準範圍。喺記錄的提交修正具體託管失敗，再重跑受影響範圍同組合。唔可以將缺少打印機的證據改稱已完成打印；取消範圍或任何指定組合仍未驗證時，唔可以標示完整矩陣已完成。

## 取消證據及限制

有界壓力測試資料用現有封閉立方體 STL，將每個頂點乘 20，變成 200 mm 立方體。經原生檔案選擇器匯入，使用普通組合操作流程相同的內附預設設定檔，並記錄產生檔案的確切雜湊。咁樣擴闊真正切片時間區間，唔使喺產品程式碼加入人為延遲。打印體積較細或缺少內附預設的打印機可能拒絕佢；呢個係測試資料不可用，唔係成功取消證據。

驅動程式最多作三次真實請求，交替使用 Slice and Print 同 Slice and Send。每次取消點擊之前，重新讀取自選觀察，要求即時相符原生世代同待處理操作，再使用目前真正繪製的命中區。呢次確切而新鮮的輸入觀察，錨定原生世代 `G`、完成序號 `S`、請求身分、模型版本、目前／處理中列印板同後續操作序號。輸入要求 `cancellationRequested=false`；計數器必須係無號 64 位元整數，唔係布林或浮點值。目前 `request_stop()` 契約將取消時期推進到 `C=G+1`，所以取消後觀察必須用 `C`，保留請求／模型／列印板身分，報告 `cancellationRequested=true`，清除待處理操作，並保持後續操作序號不變。世代位於無號最大值時，無法建立下一時期證明，會喺輸入之前被拒絕。

之後驅動程式最多等 90 秒，要求擁有權釋放，同時收到一項新的真正接收器記錄：`sequence>S`、`accepted=true`、`rejection=none`、`status=cancelled` 同 `eventGeneration=currentGeneration=C`。終端觀察仍須屬於 `C`，報告已知擁有權已釋放及已取消結果。只有結果而冇已送達且接受的事件、舊事件、未知擁有權、序號被覆寫或身分漂移，都唔可以通過。收據保留錨點、已接受事件同終端觀察。之後每次試驗都用相同匯入模型，以及更新的真實切片請求。

驅動程式喺等前一次完成之前，先嘗試下一操作。產品刻意喺工作執行緒仍擁有工作期間停用兩個組合控制項（`MainFrame::update_slice_print_status`、`enable_output`），並喺 `Plater::priv::on_action_slice_plate` 獨立拒絕另一請求。取消後觀察仍報告擁有權時，驅動程式要求下一控制項已停用，點擊其真實區域，檢查請求身分、待處理操作同後續操作不變。兩次正面擁有權觀察都必須屬於同一取消時期 `C`、請求、模型及列印板，先可以算係重疊不變條件。點擊期間完成，就令該次嘗試保持 `not_observed`。

自然送達的舊世代完成事件會另外檢查 `accepted=false` 同 `stale_generation`。成功取消範圍需要明確取消，加上真正拒絕事件或者已觀察停用重疊不變條件，兩者其中之一。如果只觀察到停用控制項不變條件，收據一定將過期完成報告為 `not_observed`。唔用注入事件或偽造延遲工作。機器無法產生任何一種證據時段，就傳回 `not_observed` 同非零退出碼。點擊失誤、世代改變、事件歷史截斷、目標不可用、切片失敗或工作執行緒掛住，都唔可以標成通過。因為切片太快而到達確認對話框時，只用 Escape 關閉。

呢啲檢查涵蓋同一列印板取消／重試，以及收據明確記錄到的重疊或過期完成證據。尚未證明模型／設定編輯、切換列印板、工作進行中關閉應用、每種平台排程交錯，或不可中斷核心的取消。唔會向硬件提交打印或傳輸。普通組合 Print 同 Send 範圍另行要求成功的目前世代完成事件，同相符且已取用的後續操作，之後先接受現有對話框作證據。即使遙測顯示已派發，缺少打印機／帳戶對話框仍屬不可用。

必需的託管審閱，目前待完成：

- [ ] 編譯呢個確切候選版本並執行版本化觀察契約。
- [ ] 觀察真正取消，待處理操作為空且後續操作序號不變。
- [ ] 觀察真正過期完成事件，喺任何目前執行變更之前被拒絕。
- [ ] 公開之前審閱每張保留圖片同加密原生記錄。
- [ ] 重複必需語言、主題、視窗大小及真實 DPI 組合。
- [ ] 獨立審閱關閉、事件次序、環形記錄截斷及原生目標新鮮度。

準備呢個擴充時，冇本機編譯、測試、原生執行或擷取。來源審閱同空白檢查唔係執行驗證。

## 同步擁有權修正證據

較早診斷呼叫 `BackgroundSlicingProcess::running()`，佢讀取普通 `m_state`。工作執行緒喺開始、完成、取消及退出時，會持有 `m_mutex` 寫入 `m_state`。因此重複 UI 診斷引入咗未同步讀取者。`automation_worker_running()` 而家用 `std::try_to_lock` 取得同一互斥鎖，爭用時傳回 `std::nullopt`，只喺 RAII 鎖持有期間評估狀態。佢唔等候、通知、排程、變更狀態或改變現有工作執行緒生命週期。現有排程器存取函式唔受呢個診斷修正影響。繪製而家只透過 `automation_slice_native_generation()` 讀取現有原子原生世代。

序列化契約喺爭用時使用 `workerStateKnown=false` 同 `workerRunning=null`。原生觀察拒絕不一致的已知／null 配對；取消驅動程式只將確切 `true` 當成持有，確切 `false` 當成釋放。未知結果只獲有界重試，絕唔計作閒置或成功。呢個包括原生輔助程式的新鮮點擊前檢查，同取消後擁有權釋放迴圈。輔助程式每次嘗試之前都清除候選矩形，所以未知觀察唔可以重用舊目標。

聚焦託管回歸要求，未喺本機執行：

- 由另一執行緒持有真正背景互斥鎖，同時請求診斷：必須唔等鎖釋放就傳回未知。釋放之後，再驗證已知狀態符合工作執行緒生命週期。
- 真正切片及取消期間重複讀取 `project_inspect`；確保每個未知工作執行緒狀態序列化成 null，絕唔計作釋放或成功停用時段觀察。
- 真正取消期間保留逐次輸入圖片，喺下一操作停用點擊前後夾住已知擁有權讀取，否則報告冇觀察到該時段。
- 過期事件拒絕同停用重疊證據保持分開。停用控制項結果絕唔代替聲稱過期完成事件曾發生。
