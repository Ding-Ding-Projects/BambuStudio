# 可攜式配套工具發佈

專用的 `lan-setup-companion.yml` 工作流程，會在託管的 Windows 2025 上透過 `build-installer.bat /s -Companion LanDropSetup` 編譯。一般原生產生工具保持不變。根目錄產生工具使用現有已驗證的 Node 啟動工具、確切的執行環境及建置工具版本、npm 鎖定檔完整性資料，以及發行者提供的執行環境總和檢查碼。

影響配套產生工具的分支推送，以及手動觸發，都會選定確切的原始碼提交。標籤推送不會觸發這個工作流程。每次執行嘗試都會獲得獨一的 `lan-setup-v<version>-<run-id>-<attempt>` 標籤。發佈會使用 `--latest=false` 建立一般版本，既非草稿亦非預先發佈版本，原生應用程式已接納的更新頻道保持不變。

四個可下載檔案分別是單一可攜式執行檔、其 SHA-256 附屬檔、`build-manifest.json` 及 `package-proof.json`。發佈程序會比較原始碼及索引身分、原始碼沒有未提交變更的狀態、輸入雜湊、確切套件版本、未封裝產物內的內嵌資訊清單，以及執行檔位元組。之後會讀回一般版本發佈、確切的輕量標籤提交，以及所有下載資產的雜湊。這不能取代獨立檢查最終執行檔內的資訊清單，或實際操作下載的套件。

唯讀 API 呼叫最多嘗試三次。建立版本發佈不會盲目重試或覆寫：必須先檢查任何部分完成的結果，再使用新的執行嘗試。綁定原始碼的編譯失敗、缺少憑證或無法下載，仍然會視為失敗。發佈會先使用儲存庫的 `TOKEN_GITHUB` 憑證，再依次使用現有的發佈權杖、組織權杖及執行權杖後備選項，不會列印其值。

編譯計時來自該次執行嘗試的工作 API 所傳回、已完成的產生步驟。時間格式會將總小時數向下取整，亦適用於超過一天的時間。只有版本發佈中繼資料及已下載資產雜湊通過讀回驗證後，發佈收據才會記錄 `publicationVerifiedAt`。工作流程仍在執行時，整個工作流程的終結時間會明確標示為未驗證。即使編譯失敗，另一個 `always()` 步驟亦會嘗試保留有界限的原始碼及執行身分、已觀察的工作及編譯結果、執行器平台和觀察時間。該診斷步驟及收據上載都採用盡力而為方式，因此儲存服務中斷不會把原本成功的發佈變成失敗工作。

發佈說明會重用 `scripts/ci/Measure-LineCount.ps1`，針對完整檢出歷史產生資料。點心中繼資料來自公開的 `Ding-Ding-Projects/dim-sum-photos` 目錄，並固定到已解析的修訂。發佈工具會搜尋完整且有界限的專案發佈歷史，找出已使用名稱及 ID，再選擇未使用的點心；其照片必須已作為 `catalog-v1*` 發佈資產上載。它會記錄確切的雙語名稱、點心 ID、目錄修訂及公開照片連結，不會複製照片。配套工具的發佈會逐一執行。其他獨立發佈工具仍可能同時選取同一道點心；這個工作流程沒有聲稱提供覆蓋整個儲存庫的預留服務。

如果目錄、歷史或已發佈照片無法取得，就會採用獲准的純版本號發佈方式，並明確註明資料無法取得。它不會虛構照片或重用已知名稱。搜尋最多讀取 20 頁發佈清單，以及每個目錄版本發佈的 50 頁資產清單；達到上限時，命名會維持未解決，不會把部分歷史當成完整歷史。

這個工作流程不會執行測試或程式碼風格檢查。它不會啟動配套工具、操作 Docker、更改服務或安裝無關應用程式。可攜式設定配套工具有明確的封裝例外；原生應用程式的 Squirrel 安裝程式要求保持不變。配套工具尚未安裝，並不代表獲准安裝另一項產品。

## 尚待取得的交付證據

這是已準備好的發佈途徑，並非已發佈版本。首次觸發、託管環境啟動準備、發佈讀回、下載後單檔啟動，以及綁定原始碼的執行驗收仍然待辦。自動取得託管依賴項目、自訂憑證、資料夾儲存及完整必要功能覆蓋仍未完成。發佈命名及行數產生尚未在託管發佈中執行。配套工具的「關於」及變更記錄介面仍未使用所選發佈點心，而整個工作流程的終結時間需要稍後讀回已完成的執行；單靠這個發佈工具，不能證明已符合完整的發佈呈現規範。
