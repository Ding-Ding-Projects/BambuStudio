# Native Windows installer

## Current packaging contract

The supported Windows installer is an unsigned Squirrel.Windows release. The packaging script
`scripts/windows/Invoke-SquirrelPackage.ps1` creates a NuGet package containing the installed native
C++ payload under `lib/net45`, then runs the hash-pinned Squirrel.Windows 2.0.1 `releasify` command.
The release directory contains:

| Asset | Purpose |
| --- | --- |
| `Setup.exe` | Squirrel bootstrapper; unsigned and may trigger an unknown-publisher or SmartScreen warning |
| `RELEASES` | Update-feed index with package hashes and filenames |
| `*-full.nupkg` | Complete install/update package, including `bambu-studio.exe` |
| `*-delta.nupkg` | Optional delta packages generated by Squirrel |
| `Setup.exe.sha256` | Locally reproducible SHA-256 sidecar |

The package nuspec records the exact 40-character source commit and HTTPS repository URL. The
wrapper validates the feed reference, the full package contents, that Setup.exe has an empty PE
security directory (unsigned), and the checksum before handing the assets to CI or a manual release.
Code signing is permanently disabled; provenance and SBOM attestations do not make an unsigned
executable signed.

## Update and install behavior

Squirrel owns installation and update staging beneath the user's profile. `Setup.exe` is the initial
bootstrapper; subsequent versions are represented by the `RELEASES` feed and full/delta packages.
The application remains usable without an installer registry entry, and the update feed is ordinary
HTTPS metadata plus package hashes. A release must never claim authenticity from the checksum alone.

The one-click wrapper does not launch Setup.exe unless `-Install` is explicitly supplied. It writes
all generated artifacts outside the source payload and refuses to continue when the payload is empty,
the version is not numeric, the source commit is not a full SHA, the repository is not HTTPS, the
package is missing `bambu-studio.exe`, or the generated Setup.exe contains an Authenticode
certificate table.

## Security and failure boundaries

- The Squirrel.Windows package is fetched from the official NuGet flat-container URL and checked
  against a committed SHA-256 pin before extraction.
- Package paths are created in a validated temporary directory and copied only into the requested
  `artifacts/windows/squirrel` output directory.
- `RELEASES` must reference the generated full package; the package must contain exactly one nuspec
  and the native executable at `lib/net45/bambu-studio.exe`.
- The checksum covers `Setup.exe` and is not a signing substitute. Users should verify it before
  launching an unsigned download.
- No certificate, private key, signing service, or signing credential is requested or invoked.

## Legacy NSIS source

`packaging/windows/BambuStudioMD3.nsi` and its helper scripts remain in the repository as historical
source for older releases and audit records. They are not invoked by the current build or release
workflow. New installer work must target the Squirrel contract above; the old NSIS UI-page and
uninstaller behavior is not a current product guarantee.

## Verification

Run the local contract checks before packaging:

```powershell
pwsh -NoLogo -NoProfile -File scripts/ci/Test-OneClickBuild.ps1
pwsh -NoLogo -NoProfile -File scripts/ci/Test-WindowsRelease.ps1
```

After a build, the CI-only validator checks the real Squirrel output on the disposable hosted
runner. It verifies the exact source commit in the nuspec, `RELEASES`, the full package contents,
SBOM metadata, the checksum, and the empty PE security directory that proves the unsigned state.
Runtime UI captures remain a separate
evidence boundary and are listed in the repository screenshot matrix.
