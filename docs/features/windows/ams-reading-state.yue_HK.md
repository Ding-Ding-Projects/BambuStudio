# 每個托盤嘅讀取指示

原生 Device 頁面使用每個托盤嘅 `DevAmsTray::is_reading()` 決定讀取動畫，與裝置網頁檢視使用同一狀態讀取器。控制項、排列、顏色、圖示同 Material Design 3 繪製全部不變。

舊原生條件要求混合 AMS Lite 托盤嘅讀取位元（`24 + tray`）同一個無關嘅普通 AMS 位元同時設定。因此托盤可能正在讀取，但原生指示仍然停住。

剖析器由所屬單元保留獨立嘅 `is_ams_lite_mixed` 讀取排列旗標。原有 `ams_type` 繼續正規化為 AMS Lite，供顯示同材料對應使用。新托盤旗標預設為 false；每次托盤更新都會喺保留設定嘅提早返回之前更新旗標，包括重用嘅混合托盤變成普通 Lite。只重設材料嘅 `reset()` 保留呢個實體單元身分，就好似保留原有單元 ID 同正規化類型一樣。

## 協定對應

| 裝置類型 | 讀取位元索引 |
| --- | --- |
| AMS、AMS Lite、AMS 2 Pro | `unit * 4 + tray`，每單元四個托盤 |
| AMS HT（`N3S`） | `16 + (unit - 128)`，每單元一個托盤 |
| 混合 AMS Lite | `24 + tray`，四個托盤 |

標準讀取器喺移位之前拒絕負索引、不支援裝置類型、超出範圍插槽，同現有 32 位元遙測欄位以外嘅位元索引。乘法之前先擴闊中間算術類型。原有無號右移工具讀取有效位元，原生顯示唔再建立有號左移遮罩。

上游開發提交 `f10ede8a3229b4ea306ac90e2ba415c867f57fd1` 建議將所有大於 127 嘅單元偏移乘四。呢個表達式冇採用：目前裝置模型將 AMS HT 視為單插槽裝置，單元 129 必須保留位元 17，而唔係移到位元 20。

## 驗證同限制

執行 `node --test ui-md3/tests/ams-reading-state.test.mjs`。針對性測試抽取產品 C++ 類型讀取方法、剖析器賦值、對應、讀取器同原生決定本體，喺 JavaScript 模型執行算術。涵蓋每托盤隔離、混合 Lite 單獨高位元、普通 AMS 系列、HT 單元 129、閒置狀態、無效插槽／類型，同位元 31 算術邊界，亦涵蓋重用托盤由混合轉為普通嘅狀態。首次修正前，原有判斷式同無效移位被拒絕。由剖析器衍生嘅後續檢查再揭露首個候選遺失混合身分：保留獨立旗標之前八項中五項通過，修正後八項全部通過。

呢啲係源碼衍生回歸證據，唔係原生編譯、繪製或者實體打印機證據。原有 `stol` 遙測剖析器同字串識別碼剖析不變。尤其儲存位元 31 嘅算術測試，唔代表 Windows 剖析器接受無號高位元十六進位字串。裝置韌體／協定行為仍需硬件驗證。呢個指示計算唔會發送打印機命令。
