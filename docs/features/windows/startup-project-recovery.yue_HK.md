# 復原啟動時無法重新開啟的專案

如果上次使用的專案遺失、無效，或載入途中中斷，應用程式會保留它的分頁及檔案，並開啟另一個「未命名」分頁。復原訊息會說明兩個可用操作：

- 選取保留的專案分頁，明確要求重試，例如找回遺失的檔案或替換損壞的副本後。
- 使用 **檔案 > 開啟** 選擇另一個專案。

啟動時的自動還原現在使用明確的執行情境，與原有靜默匯入旗標分開。它不會建立載入進度對話框；失敗或延後審閱時，會使用非模態通知。手動重試分頁、「檔案 > 開啟」及其他呼叫方式預設仍然維持互動，包括原有的匯入診斷及安全決定。程式不會自動接受版本、G-code、打印機同步、紋理或縮放方面的決定。

目前的自動還原範圍刻意保守。文件必須處於尚未修改的初始狀態，沒有待處理的預設變更、已選取裝置或待顯示的裹料偵測指引。獨立解析必須確認它是受支援版本的原生專案，沒有設定替代或內嵌預設、不涉及紋理匯入，使用通過驗證且源自系統的預設，亦沒有需要決定的已修改 G-code。正規化後的完整設定必須與目前啟用的設定一致，包括打印機及熱床。物件和體積層級除耗材分配以外的覆寫設定，以及需要大型物件縮放的幾何資料，都需要明確審閱。目前只要有內嵌預設就會延後還原，是因為現有解析器沒有唯讀的決策預覽，並不代表每個內嵌預設都不安全。

准入檢查在套用打印盤、預設或設定之前進行。獲准自動載入的專案會保留已經相符的設定，而不呼叫預設編輯器，因為其更新流程可能顯示調整對話框。延後載入或套用前失敗時，會保留初始文件而不重設其預設。只有開始套用後才發生的失敗，才會使用原有復原重設。保留的目標及待處理標記仍可供使用者明確重試。這個較窄的自動範圍不代表每個原生專案都能無需互動地還原，也不代表未能還原的專案已經損壞。

空白工作分頁沒有檔案身分，因此儲存它不會覆寫保留的專案。重試失敗時，原先的文件會繼續保持作用中，而失敗的目標亦會保留。原有的未儲存文件檢查仍然適用。

自動還原前，應用程式會在原有本機設定中儲存 `project_tab_recovery.pending_path`。自動載入器獲准執行之前，必須從磁碟上有大小限制的 JSON 讀回待處理標記；寫入未能驗證時，目標會保留供明確復原。啟動中斷後，不會再次自動嘗試同一個待處理路徑。成功還原、成功明確重試分頁、透過「檔案 > 開啟」成功開啟相同路徑，或接納另一啟動流程已載入的同一專案，都會清除相符標記。開啟失敗及成功開啟其他路徑則會保留標記。還原失敗會持久儲存另一個空白作用中分頁，讓之後正常啟動不會反覆嘗試保留的無效檔案。這項復原不會刪除任何模型或快照。標記屬於本機路徑，適用於現有已儲存專案分頁路徑的同一私隱界線；此功能不會匯出標記或將它傳送到服務。

已儲存的專案檔案使用一般專案載入器。私人未儲存快照會保留原有還原語義，並在載入後恢復原本的專案檔名。另一啟動流程已建立的文件會保留，並綁定到相符或新建的分頁，包括未命名的匯入幾何資料及有未儲存變更的文件。如果因無法保留目前歷史而取消建立空白復原專案，就不會聲稱已建立或啟用空白分頁。

## 驗證

已安裝的 2.9.1932 版本 `md3-v260`，原始碼 `dac16c242c95ac07c9913bf40cf05dbc508b69de`，執行檔 SHA-256 `96d2c9b82ea2675a258221563b597bd9b84c190ffac73f9bedaf4725fd2af168`，曾使用兩個由測試擁有、互相隔離的資料目錄，在不同隱藏桌面進行比較。兩份設定檔都以換行字元結尾。其中一份含有已儲存分頁，指向一個實際存在、人工建立的無效 `.3mf`；對照組則沒有已儲存專案分頁。

無效檔案情境顯示 **Loading of a model file failed.**，對照組則到達首頁，帶有空白「未命名」分頁，沒有相同錯誤對話框。兩張實際影像都已檢視。這證明了一條可重現的已儲存分頁載入失敗路徑，但未能確定個別使用者啟動報告的原因。私人執行紀錄及擷取影像保留在儲存庫以外。沒有手動修改真實使用者設定檔、專案或個人用語快取。空白對照組其後顯示網絡外掛安裝完成對話框；這次驗證並沒有發出安裝命令。該版本的 `--datadir` 不會隔離獨立的個人用語快取，因此這些執行沒有匯入或重設個人用語。

`node tests/startup_recovery_behavior.test.mjs` 會編譯並執行實際的啟動、明確切換及回復函式，配合確定性的載入器、設定及介面替身，以及真正有大小限制的標記檔案解析。涵蓋無效或遺失檔案、還原中斷、成功還原、明確重試成功與失敗、載入期間的標題回呼、空白啟動、其他啟動流程已建立的文件、私人快照身分、取消重設、未命名幾何資料，以及設定寫入失敗。修改後的原始碼通過檢查；相同可執行檢查針對 `d17122fa8ec2ae1da871e677aa3dce3beda94c92` 則回報 19 項斷言失敗。測試亦檢查明確重試分頁、「檔案 > 開啟」及已載入的啟動文件會清除相符標記；開啟失敗及其他路徑必須保留標記。

同一個實際流程測試亦檢查自動與手動情境、非模態復原、不需決定的還原、延後審閱而沒有模擬套用預設，以及明確互動式重試。`--interactive-startup-mutant` 選項會刻意移除自動准入，必須令測試失敗。`node tests/startup_nonmodal.test.mjs` 會以中性的封存資料及設定替身，執行實際的獨立准入區塊與正式進度包裝器。它檢查一個獲准情境、十一類延後情境、沒有推測性套用、釋放待處理資源，以及互動式進度取消。`--admission-mutant` 會移除延後分支，必須失敗。

同一測試亦會使用幾何替身，執行從實際下游程式擷取的條件及擺放呼叫：獲准的自動及手動原生專案會保留負 Z 座標及零體積物件，而手動幾何匯入則保留原有清理及擺放流程。`--classification-mutant` 會移除自動專案分類，必須因這些下游影響而失敗。這些測試不會解析真正的 3MF、操作實際預設編輯器，亦不能證明每條間接原生路徑都不使用模態對話框。仍然需要原生編譯及情境證據。

替身不能證明原生封存解析、正式 AppConfig 持久儲存或實際顯示的復原行為。聲稱修正已通過端到端驗證之前，仍須進行原生編譯及相同的隱藏桌面情境，包括重新啟動、修復檔案後重試、「檔案 > 開啟」，以及保護切換前未儲存的內容。
