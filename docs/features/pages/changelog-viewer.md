# Changelog viewer

Every release this fork has published, newest first — not just the latest. Viewer:
[`ui-md3/site/changelog.js`](../../../ui-md3/site/changelog.js). Data:
[`ui-md3/site/changelog.data.js`](../../../ui-md3/site/changelog.data.js), generated by
[`ui-md3/scripts/build-changelog.mjs`](../../../ui-md3/scripts/build-changelog.mjs).

## Where the content comes from

Nothing in the viewer is written by hand.

- Version, name, dish, publication date, release URL, commit, CI run link and attached files with
  their byte sizes come from the GitHub Releases API.
- The change lines under a release are the **commit subjects between that release's tag and the
  previous release's tag**, read from `git log`.
- The category badge on each line is derived mechanically from the commit subject's leading verb
  (`fix…` → Fixed, `add…` → Added, `remove…` → Removed, `document…`/`handoff…` → Documented,
  otherwise Changed). The viewer states this derivation on the page, so a miscategorised line reads
  as a mapping artifact rather than a claim.
- A release with no commits in its range says so. A release whose tag points at the **same commit**
  as its predecessor says *that* instead — a different fact, and the only one of the two that has
  actually been checked. The oldest release says it has no earlier release to compare against. None
  of the three is padded with filler.

Regenerate locally with `node ui-md3/scripts/build-changelog.mjs`. **CI regenerates it at deploy
time** from the Releases API under `continue-on-error`, with the committed file as the outage
fallback — so the published site lists every release, including ones published after the file was
last committed.

A published release also redeploys the site, so it appears without waiting for the next push —
but not directly. The `github-pages` environment on this fork accepts deployments only from
`master`, and a `release` event runs at the **tag** ref, so the deploy job was rejected before its
first step: a three-second failure with no steps and no log. It failed that way 12 times out of 12
before anyone noticed, and the refresh it promised never happened once. The release event now goes
to a `redeploy-on-release` job that holds no environment and simply dispatches this workflow on
`master`; that run lands as `workflow_dispatch` and deploys normally. It needs a real PAT —
`GITHUB_TOKEN` cannot trigger another run — and says so in the log rather than failing if none is
configured. [`ui-md3/tests/site.test.mjs`](../../../ui-md3/tests/site.test.mjs) asserts the shape.

There is deliberately **no freshness gate**. Requiring the committed file to be current looked
tidy and was a trap: every release CI publishes makes it stale by definition, so the next Pages
deploy would fail until a human regenerated it by hand. `--check` still exists as a local
convenience and stands down (exit 0) when the GitHub API is unavailable.

## One calendar: UTC

A release timestamp is a UTC instant, and the day a release is filed under is its UTC day. Every
bound this view produces is therefore a UTC day too — the presets, the calendar cells, the typed
dates and the export header all agree. Building the bounds from the local calendar instead put the
newest release outside "last 7 days" for anyone west of Greenwich, which is the kind of bug that
only ever reproduces for other people.

## Date filter

- **Typed dates.** The `From` and `To` fields accept a plain ISO date (`2026-07-28`, and
  `2026-7-8`) or the visitor's own locale format, whose field order is read from
  `Intl.DateTimeFormat` rather than assumed. Input that does not parse — including impossible dates
  like `2026-02-30` — is reported inline and **leaves both the filter and the typed text alone**.
- **Calendar.** Each field opens a month grid with previous/next month buttons, a month select and
  a year select for jumping, and the current range highlighted. Choosing a day that would put the
  start after the end swaps them instead of emptying the view.
- **Presets.** All time, last 7, 30 and 90 days.

## Search

The search bar is the shared component: plain text by default, regex on explicit opt-in, the full
builder one button away, with the changelog itself as the builder's sample. It matches the tag,
name, version, both dish names, the qualifier, the commit and every change subject.

Search and date filter **compose**: narrowing one never widens the other, and the count line always
states "N of M releases". When the two together match nothing, the empty state says so honestly
rather than showing an unfiltered list.

## Copy and export

**Copy view** puts the current filtered view on the clipboard; if the browser refuses clipboard
access the text is selected instead and the notification says to press <kbd>Ctrl</kbd>+<kbd>C</kbd>.
**Export Markdown** downloads exactly what is displayed, in a file named for the active range, whose
header states the source, the exported range, the active search, the number of releases exported out
of the total, and the category derivation.
